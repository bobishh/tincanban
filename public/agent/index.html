tincanban agent guide

Operate the same local-first workspace the user sees. Read stable IDs first, then mutate typed entities through WebMCP commands.

Core ruleRead schema.
Use IDs.

Working model

A device owns a local catalog of independent workspaces. Each workspace has an active Automerge document containing its board schema, items, document templates, and collaboration metadata. Earlier original changes can live in separately verified history archives. WebMCP commands target the current workspace shown in tincanban; creating a workspace makes it current.

  • Every entity has a stable UUID. Titles are display text and may change.
  • placement.parentId links a column to its board, an item to a column or parent item, and an artifact to its item. placement.rank orders siblings.
  • Archive marks items archived. Enable one Archive column per board to show and restore them.
  • Removing a column hides its descendants; restoring the column reveals them with their relationships intact. Broken or cyclic ancestry appears through placement issues.
  • Job search is one preset. Its lead vocabulary and pipeline are workspace-specific, never kernel assumptions.

Safe agent workflow

  1. Call list_workspaces to inspect the local catalog. Use switch_workspace with the chosen workspaceId when the task requires an existing workspace. Creating or switching changes the current workspace shown to the user.
  2. Call get_workspace_settings. Resolve board, column, field, option, and template IDs from its result.
  3. Read items with list_items or inspect one typed entity with get_entity.
  4. Use generic mutation tools. Put custom values under stable field IDs, not field titles.
  5. Re-read visible state after mutations. Treat returned IDs and CRDT heads as authoritative.

Complete workspace settings

get_workspace_settings returns settings plus heads. Settings contain formatVersion, workspace.title, the board title and item name, column colors and archive behavior, card stage buttons, aging thresholds, priorityPolicy, employee_profile, typed fields and select options, and documentTemplates. Templates belong to that workspace and describe documents generated for its items; they have no fixed CV/cover-letter kind enum.

To change the complete configuration, edit the returned object and call apply_workspace_settings with those heads as expectedHeads. The apply is one validated CRDT transaction. Omitted columns, fields, and templates are soft-archived. Existing descendants and field values remain stored.

Keep IDs returned by tincanban when editing. Omit an ID only when adding a column, field, field option, or document template. A field's valueType cannot change in place.

Mutation rules

  • Unknown fields are rejected without mutation. Send command inputs, never raw Automerge objects or changes.
  • Keep returned IDs. Names are editable labels and cannot identify an entity safely.
  • Use expectedHeads for settings writes. On a conflict, re-read settings, reapply the intended edit, and submit the new heads.
  • Use restore_and_move when an entity's former parent is archived or missing. Do not repair ancestry by recreating the entity.
  • Inspect list_placement_issues only for recovery. Normal parent/child relationships need no repair.

Sync, identity, and storage

  • Share workspaces: Sync opens with the current workspace selected. Select one or more existing workspaces, then generate one invitation for that fixed set. The recipient keeps a separate person and device identity.
  • Add my device enrolls another device under the same personal identity; it is different from inviting another person to a workspace. Compare the authentication code on both devices; the existing device owner approves enrollment. Confirmed devices transfer signed identity/catalog and profile state plus private Rusty settings over their authenticated device channel. Board copies still need device or Rusty sync, and each device keeps its own replication progress.
  • Recovery backup can restore the same identity, profile, workspace references, and private Rusty settings on a replacement device. It does not contain board history or attachment bytes; those need a workspace backup or an available Rusty copy. Older seed-only recovery files restore only the identity key.
  • If Sync → Rusty shows Update device access, an owner can update Rusty's signed permission policy for approved devices. This keeps boards, saved files, and device certificates unchanged.
  • Rusty statuses describe recent confirmation for each board: Not checked, Syncing, Catching up, Synced, Check overdue, Unavailable, or Removal pending. Synced means a successful check within the last 45 seconds. Profile delivery appears separately; it is not a claim that the whole board copy is synced.
  • Sync contains Participants, Rusty, Backups, and Recovery. Import as a new board belongs to the Workspaces list; export belongs to Sync → Backups.
  • Rusty stores encrypted objects without reading or classifying cards. Eligible owners replace redundant storage snapshots after 8 retained objects; that operation keeps the inner Automerge history. Separately, Owner-authorized history compaction runs at 512 admitted active changes or 4 MiB of active history. Original changes and their classifications remain in archives; total retained storage can still grow.
  • Automerge changes sync incrementally while peer sessions are live. Workspace snapshots and trust state persist in IndexedDB.
  • A .tincanban export carries workspace data, Automerge history, and public proofs. It excludes private signing keys, the personal root, and pairing secrets.
  • Load earlier history in an item's History section reads archived revisions on demand. Restoring one creates a new currently authorized change and keeps the original revision and its provenance.
  • Sync → Backups → Private recovery backup encrypts original workspace evidence, available archive and attachment bytes, and private reading keys with separate recovery words. A peer-received archive can be backed up without Rusty credentials. Missing archive or attachment parts make coverage explicitly incomplete. Inspect before restoring; replacing an existing workspace requires confirmation.

Settings and publication

With a board open, Settings sections are Identity, Workspace, Document templates, Priority rules (when supported), and settings.json. Identity saves name and photo together with Save profile; Recovery backup opens a separate encrypted backup/restore flow. That file restores identity, profile, workspace references, and private Rusty connections, not board history or attachment bytes. Workspace shows local save status, automations, Public board access, and device diagnostics. Diagnostic consent applies across workspaces on this device.

Public board is an owner-only switch with a scope confirmation. Publication creates a saved public copy; later edits remain private until Update public copy. Withdrawing removes access to that copy and its files, but cannot recall downloaded copies. Publication is separate from workspace settings and has no WebMCP tool.

CLEF supplies vacancy assessments through approved automations. Website job intake can create Leads; an owner can enable forwarded email after a receiving route is configured. New source-backed applications retain the original URL-extracted company, role, text, time, and posting URL, plus captured thread references and ATS identifiers when available. Email matching uses those original references and posting evidence; editable card titles and company/role fields, and later page refreshes, do not replace the original evidence. Missing, conflicting, or ambiguous evidence stays in review. The signed automation API lets an owner bind a retained email to the chosen application and retry it; Settings does not provide a manual email review queue. Original posting evidence remains attached to its application.

Automatic priority computes fit and priority from saved assessments; it does not start or stop CLEF. Job match uses company recognition 20%, stability 20%, stack 30%, and work profile 30%. Missing evidence contributes no points. Profile edits invalidate old stack/work comparisons; historical cards are not automatically reclassified. Preserve existing weighted rules unless the user requests conversion.

Board cards drag with their full content. Select text and open contextual discussions inside a card’s details.

Run locally

Install pinned dependencies with npm ci, then start Vite with npm run dev. Workspaces remain in that browser profile's IndexedDB. Production builds use npm run build. Changes to the canonical Native policy or transport source require rebuilding its WASM package.
